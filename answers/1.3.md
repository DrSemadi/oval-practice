# Часть 3. Упрощение формата

Я свел упрощение формата к трем этапам:
* Разрешение зависимостей (ссылок)
* Оптимизация классов
* Оптимизация criteria

## Разрешение зависимостей

Ссылки представляют собой обьекты, содержащие атрибут, оканчивающийся на _ref:

Пример:
```xml
<criterion comment="Red Hat Enterprise Linux must be installed" test_ref="oval:com.redhat.rhba:tst:20191992005"/>
<red-def:object object_ref="oval:com.redhat.rhsa:obj:20236887023"/>
<red-def:state state_ref="oval:com.redhat.rhsa:ste:20269689001"/>
```

Каждый такой обьект ведет соответственно к `test`, `object` или `state` с таким же `id`. 
Для разрешения ссылки достаточно подставить элемент с таким же идентификатором на ее место.


## Оптимизация классов

1. Удален класс `metadata`, существующий в каждом `definition`.
Согласно спецификации он содержит исключительно человекочитаемую информацию и не предназначен для машинной обработки.
Согласно заданию нам нужны только нужные для детекта поля.

2. Удаление ненужных общих атрибутов. Пример: `version`, полезен для версионирования патчей, ненужен для детекта.
`id` при этом остается, так как используется в разрешении зависимостей и полезен для логирования и чтобы не терять связи между изначальным
xml-обьектом и обьектом упрощенного формата.

3. Явно указаны скрытые дефолты. Пример: в класс test теперь всегда пишутся
`check_existence` и `state_operator`. Если изначальный класс не содержал поле - используется дефолт.
Для `object` теперь есть свой ключ, как и для `states`. 
Первый ведет к словарю (object всегда 1), второй к списку (states может быть как 0, так и неограниченное число)
Пример test: 
```json
{
    "id": "oval:com.redhat.rhba:tst:20191992005",
    "check_existence": "at_least_one_exists",
    "check": "none satisfy",
    "state_operator": "AND",
    "object": {...},
    "states": []
}
```
4. Классы объектов получили свои атрибуты, позволяющие быстрее доставать из них нужную информацию. 
На данный момент поддерживается упрощенный формат для `rpminfo_object`, `rpmverifyfile_object`, `textfilecontent54_object`.
Непокрытые классы объектов получат базовый класс Object, сохраняя все дочерние классы, просто без возможности достать их по ключу.

## Оптимизация criteria
В текущем виде criteria представляет собой дерево из вложенных OR и AND (еще ONE и XOR, но их нет в файле, поэтому не рассматриваем).
Такой формат плохо поддается машинной обработке, и даже читать его вручную становится сложно с увеличением вложенности.

Поэтому было принято решение привести набор условий к `DNF` (Disjunctive Normal Form), или `OR of ANDs`.
Фактически это разбивает дерево на список тест-кейсов:

* `Тест-кейс` - набор тестов, чтобы тест-кейс был равен `True` каждый тест в нем должен быть равен `True`;
* Чтобы проверить, что нужно применить патч, достаточно чтобы хоть один его тест-кейс равнялся `True`.

Таким образом сканеру достаточно запускать тест-кейсы по очереди, пока хоть один из них не выдаст `True`.

Пример изначальной `criteria`:
```xml
<criteria operator="OR">
  <criterion comment="Red Hat Enterprise Linux must be installed" test_ref="oval:com.redhat.rhba:tst:20191992005"/>
  <criteria operator="AND">
   <criterion comment="libyang is earlier than 0:1.0.184-1.el8" test_ref="oval:com.redhat.rhea:tst:20211906001"/>
   <criterion comment="libyang is signed with Red Hat redhatrelease2 key" test_ref="oval:com.redhat.rhea:tst:20211906002"/>
   <criteria operator="OR">
    <criterion comment="Red Hat Enterprise Linux 8 is installed" test_ref="oval:com.redhat.rhba:tst:20191992003"/>
    <criterion comment="Red Hat CoreOS 4 is installed" test_ref="oval:com.redhat.rhba:tst:20191992004"/>
   </criteria>
  </criteria>
 </criteria>
```

> Замечание по поводу DNF
> 
> Подход с конвертацией criteria в DNF имеет несколько недочетов.
> 
> Первый - чем больше OR, тем больше кейсов. При большой вложенности условий количество строк в упрощенном формате
> становится гораздо больше чем в изначальном.
> Однако т.к. этот формат предназначен для обработки скриптом, минус считаю несущественным.
> 
> Второй - обязательно нужно кешировать результаты тестов. Конечно это было понятно и по старому формату, 
> учитывая что все патчи в файле могут содержать один и тот же тест, 
> но все таки проговорю явно. DNF дублирует тесты, и без кэширования будет много повторов даже в рамках одного патча.
